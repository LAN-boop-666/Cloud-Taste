# Cloud-Taste 性能测试报告

## 结论

本次测试在独立的 `cloud_taste_loadtest` 数据库和测试后端 `8081` 端口完成，没有使用正式库进行压力测试；正式库只做了订单号数据核验和唯一索引同步。

最重要的结果有四个：

1. 小规模下单请求在 5、10、20、50 个虚拟用户的阶梯测试中均为 0% 错误。
2. 修复前 50 个线程瞬时启动、每线程 3 轮时，150 次下单产生了 56 个重复订单号差额；改为 UUID 并增加唯一索引后，同样场景 150 次下单全部成功且订单号全部唯一。
3. 修复后的下单接口在 100、200、500、1000 个虚拟用户逐步启动时均为 0% 错误；1000 个用户瞬时启动时错误率为 23.72%，失败原因是连接被拒绝，不是订单号重复。
4. 订单历史查询在 100、500、1000 个虚拟用户逐步启动时均为 0% 错误；1000 个用户瞬时启动时错误率为 12.86%，643 个失败请求全部是连接被拒绝。

### 1000 用户瞬时启动

参数：

```text
线程数：1000
Ramp-Up：0 秒
每线程循环：3 次
请求总数：6000
```

结果：

```text
错误数：1423
错误率：23.72%
平均响应时间：5953.45 ms
P95：9850 ms
P99：11388 ms
最大响应：14775 ms
```

错误拆分：699 次加购物车连接被拒绝，42 次提交订单连接被拒绝，682 次提交订单因前置加购物车失败而购物车为空。没有发现订单号重复。

这说明本地单体服务可以稳定承载逐步进入的 1000 个虚拟用户，但无法把 1000 个连接在同一时刻全部压入。后续若要提升瞬时承载能力，应单独调整连接队列、线程池和数据库连接池，并重新压测，不能把这次结果解释成业务代码全部失败。

### 修复前的问题

`OrderServiceImpl` 当前通过：

```java
orders.setNumber(String.valueOf(System.currentTimeMillis()));
```

生成订单号。

并发线程在同一毫秒内执行时，会生成相同订单号。这个问题与数据库自增主键不同：主键仍然可以不同，但业务订单号可能重复。

修复方案：

- 使用去横线 UUID 生成 32 位订单号。
- 数据库为 `orders.number` 增加 `uk_orders_number` 唯一索引。
- 保留重复提交和并发下的唯一性测试。

数据库核验结果：订单总数、非空订单号数和不同订单号数均为 50150，重复查询无结果；正式库原有 18 个订单号也已确认无重复、无空值。

本次复测结论：订单号并发唯一性问题已修复。

## N+1 查询优化

优化前，订单历史查询先分页查询订单，再对每个订单调用一次订单明细查询：

```text
1 次订单分页查询 + 每个订单 1 次明细查询
```

一页 10 条订单时，可能产生约 11 次 SQL。优化后先收集当前页订单 ID，再批量查询明细并在 Java 中按 `order_id` 分组组装，列表查询的明细访问降为 1 次批量查询。

## SQL 学习结论

以下概念不能混为一谈：

- `select *`：查询所有字段。
- 全表扫描：执行计划中的访问方式，常见表现为 `type=ALL`。
- `INNER JOIN`：表连接语义，不保证自动变快。

当前销量查询中的旧式写法：

```sql
from orders o, order_detail od
where o.id = od.order_id
```

本质上已经表达了内连接。规范写法可以改成：

```sql
from orders o
inner join order_detail od on o.id = od.order_id
```

改写主要提升可读性和维护性，最终性能仍要以 `EXPLAIN` 和压测为准。

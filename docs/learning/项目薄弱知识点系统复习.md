# 苍穹外卖项目薄弱知识点系统复习

> 用途：项目收尾后的复习与面试式自测。
>
> 适合先看“结论”，再看“项目例子”，最后完成文末自测。

## 1. 先建立整体地图

一个请求在项目中的典型路径：

```text
Vue 页面
  -> Axios
  -> 开发代理或 Nginx
  -> Spring Boot
  -> 登录拦截器
  -> Controller
  -> Service
  -> Mapper / MyBatis
  -> MySQL 或 Redis
  -> Result / VO
  -> Axios
  -> Vue 更新页面
```

各层职责：

| 层 | 主要职责 | 不应该承担的职责 |
|---|---|---|
| Controller | 接收 HTTP 请求、参数、调用 Service、返回结果 | 编写复杂业务和大量 SQL |
| Service | 业务规则、事务、状态流转、组织多个操作 | 处理 HTTP 细节 |
| Mapper | 调用 MyBatis 执行增删改查 | 决定订单业务规则 |
| Entity | 对应数据库实体结构 | 直接作为所有接口返回对象 |
| DTO | 接收前端提交的数据 | 代表数据库完整记录 |
| VO | 组装给前端展示的数据 | 代替数据库持久化对象 |

例如：

```text
OrdersSubmitDTO：用户提交订单时传入的地址、支付方式、备注等
Orders：orders 表对应的订单实体
OrderVO：返回前端的订单信息和订单明细组合对象
```

## 2. Spring 事务：保证一组操作一起成功

### 2.1 事务的核心

事务不是防止线程卡住，而是保证数据库操作的**原子性**：

```text
要么全部成功，要么全部失败
```

用户下单通常包含：

```text
1. 新增订单
2. 新增订单明细
3. 清空购物车
```

如果第 2 步失败，而第 1 步已经成功，就可能出现“有订单但没有明细”的不完整数据。因此这些数据库操作应该放在同一个事务中。

```java
@Transactional
public void submitOrder(OrdersSubmitDTO dto) {
    // 新增订单
    // 新增订单明细
    // 清空购物车
}
```

### 2.2 为什么 catch 后可能不回滚

Spring 需要感知异常，才能根据异常决定回滚。如果异常被吃掉，方法正常结束，Spring 可能提交事务：

```java
@Transactional
public void submitOrder() {
    try {
        saveOrder();
        clearCart();
    } catch (Exception e) {
        log.error("下单失败", e);
        // 没有继续抛出异常，事务可能不会回滚
    }
}
```

常见正确写法：

```java
@Transactional
public void submitOrder() {
    saveOrder();
    clearCart();
}
```

或者记录日志后继续抛出：

```java
catch (Exception e) {
    log.error("下单失败", e);
    throw e;
}
```

### 2.3 事务不能回滚外部系统

数据库事务通常只能管理数据库连接中的操作，不能自动撤回：

```text
已经发送的 WebSocket 消息
已经调用的微信支付
已经发送的短信
已经完成的 Redis 写入
```

例如：

```text
数据库更新成功
-> WebSocket 已通知商家
-> 后续数据库操作失败
-> 数据库回滚，但消息已经发出
```

常见处理方式：

- 数据库事务提交成功后再发送通知
- 使用事务事件
- 使用消息队列
- 对失败消息进行重试或补偿
- 重要业务保存消息发送记录

项目里的 `paySuccess` 既更新订单，又发送 WebSocket 来单提醒，学习阶段可以理解流程；生产设计时应进一步考虑“提交成功后再通知”。

## 3. MyBatis：参数绑定、动态 SQL 和结果

### 3.1 `@Param` 是参数别名映射

```java
List<Map<String, Object>> getEveryDayOrderCount(
        @Param("beginTime") LocalDateTime begin,
        @Param("endTime") LocalDateTime end
);
```

它建立的关系是：

```text
Java 参数 begin
  -> MyBatis 名称 beginTime
  -> SQL 中的 #{beginTime}
```

它主要是 MyBatis 的运行时参数绑定，不是 Java 编译器的功能。

单参数通常可以不写：

```java
Orders getById(Long id);
```

多个参数建议明确加上 `@Param`，否则 MyBatis 可能只能识别为 `arg0`、`arg1`、`param1`、`param2` 等名称。

### 3.2 动态 SQL 到底解决什么

动态 SQL 解决的是“查询条件是否拼接”，不是“没有数据的日期是否自动生成”。

```xml
<select id="countByMap" resultType="java.lang.Integer">
    select count(id) from orders
    <where>
        <if test="begin != null">
            and order_time &gt; #{begin}
        </if>
        <if test="end != null">
            and order_time &lt; #{end}
        </if>
        <if test="status != null">
            and status = #{status}
        </if>
    </where>
</select>
```

Java 传入：

```java
Map map = new HashMap();
map.put("begin", beginTime);
map.put("end", endTime);
map.put("status", null);
```

最终大致生成：

```sql
select count(id)
from orders
where order_time > ?
  and order_time < ?
```

三个关键部分：

- `Map`：携带可选查询条件
- `<if>`：条件存在才拼接
- `<where>`：自动添加 `where`，并清理开头多余的 `and` 或 `or`

如果所有 `<if>` 都不成立，最终是：

```sql
select count(id) from orders
```

它统计整张表的数量，不是返回所有订单记录。

### 3.3 `#{}` 与 `${}`

#### `#{}`：预编译参数

```sql
where username = #{username}
```

底层类似：

```sql
where username = ?
```

参数单独绑定，用户输入通常会被当作值处理。

#### `${}`：直接替换 SQL 文本

```sql
order by ${column}
```

它可能把用户输入直接拼进 SQL，存在 SQL 注入风险。必须使用白名单：

```text
允许值：id、name、create_time
其他值：直接拒绝
```

普通查询值优先使用 `#{}`。

### 3.4 `COUNT`、`SUM` 和空结果

没有符合条件的数据时：

```sql
select count(id) from orders where ...;
```

通常返回：

```text
0
```

而：

```sql
select sum(amount) from orders where ...;
```

通常返回：

```text
NULL
```

所以项目中需要处理：

```java
turnover = turnover == null ? 0.0 : turnover;
```

必须记住：

```text
COUNT 没数据 -> 0
SUM 没数据   -> NULL
```

### 3.5 `GROUP BY` 为什么不会返回空日期

```sql
select date(order_time), sum(amount)
from orders
group by date(order_time);
```

如果订单只有 8 月 1 日和 8 月 3 日，SQL 只会返回：

```text
8月1日
8月3日
```

不会凭空生成 8 月 2 日，因为数据库只能对实际查询到的记录分组。

当前项目采用：

```text
Java 生成完整日期列表
-> SQL 查询有数据的日期
-> 结果放入 Map
-> 遍历完整日期
-> 缺失日期使用 getOrDefault 补 0
```

所以动态 SQL 和日期补零是两件事：

```text
动态 SQL：决定查询条件
Java 补零：保证日期和数据一一对应
```

### 3.6 `INNER JOIN` 与 `LEFT JOIN`

```sql
orders o inner join order_detail od on o.id = od.order_id
```

如果订单没有明细，整行不会出现在结果集中。

```sql
orders o left join order_detail od on o.id = od.order_id
```

即使没有明细，订单仍然返回，明细字段为 `NULL`。

```text
INNER JOIN：只保留两边都匹配的数据
LEFT JOIN：保留左表全部数据
```

商品销量统计使用订单明细关联订单，并限制：

```sql
o.status = 5
```

这样只统计已完成订单。否则待付款、已取消等订单也可能被计入销量。

### 3.7 报表查询的性能

如果循环 30 天，每天执行订单数、有效订单、营业额、新用户等多次 SQL，可能产生一百多次查询。

优化方向不是“只传一个 Map”，而是重写查询：

```sql
select date(order_time) as day,
       count(id) as total_order_count,
       sum(case when status = 5 then 1 else 0 end) as valid_order_count,
       sum(case when status = 5 then amount else 0 end) as turnover
from orders
where order_time >= ? and order_time <= ?
group by date(order_time);
```

即：

```text
一次查询整个时间范围
-> GROUP BY 日期
-> 条件聚合
-> Java 补齐缺失日期
```

### 3.8 索引的基本判断

对于：

```sql
where user_id = ?
  and status = ?
  and order_time between ? and ?
```

可以考虑：

```text
(user_id, status, order_time)
```

原因是：

- `user_id` 是等值条件
- `status` 是等值条件
- `order_time` 是范围条件

联合索引通常把等值条件放在范围条件前面。`begin` 和 `end` 是传入的参数，不是数据库字段，真正可能建索引的是 `order_time`。

最终是否有效要用 `EXPLAIN` 验证，并结合实际查询频率、数据量和写入成本判断。

## 4. 订单状态、权限和幂等

### 4.1 状态和支付状态是两套概念

订单状态描述订单业务阶段：

```text
待付款 -> 待接单 -> 已接单 -> 派送中 -> 已完成
```

还可能有取消分支：

```text
待付款 -> 已取消
待接单 -> 已取消或拒单
```

支付状态描述资金状态：

```text
未支付 -> 已支付 -> 已退款
```

支付成功后，项目通常会做：

```text
pay_status：未支付 -> 已支付
status：待付款 -> 待接单
记录支付时间
发送商家来单提醒
```

### 4.2 为什么不能相信前端 status

下面的写法危险：

```java
orders.setStatus(dto.getStatus());
orderMapper.update(orders);
```

用户可以绕过页面，直接发送：

```json
{"status": 5}
```

从而可能跳过支付、接单和配送，直接把订单改成完成状态。

正确方式是每个业务方法决定目标状态：

```java
// 接单方法内部决定只能变为已接单
orders.setStatus(Orders.CONFIRMED);
```

### 4.3 商家接单的校验

至少检查：

```text
1. 订单是否存在
2. 当前操作者是否通过商家端登录校验
3. 当前订单状态是否为待接单
4. 支付状态是否符合要求
5. 订单是否已取消或超时
6. 重复接单是否需要幂等处理
```

当前项目是单商家项目，订单表没有 `merchant_id`，所以暂时不需要检查商家归属。多商户系统必须增加这项校验。

### 4.4 幂等是什么

幂等表示同一个操作执行一次和多次，最终结果一致。

```text
重复点击支付不能重复扣款
重复接单不能重复处理
重复支付回调不能重复发放业务结果
```

防重复下单可以使用：

- 前端提交后禁用按钮：改善体验，但不能作为唯一防线
- 请求唯一号 `requestId`：数据库设置唯一约束
- Redis 一次性 Token：后端原子消费
- Redis `SETNX`：用用户和请求号建立短期锁
- 数据库唯一索引：最后一道防线

### 4.5 支付幂等

支付前应该检查：

```text
订单存在
订单属于当前用户
订单处于待付款状态
支付状态是未支付
订单没有取消或超时
金额与支付请求一致
```

支付成功通知不能只依赖普通查询加 `if`，因为两个请求可能同时读到“未支付”。更可靠的是条件更新：

```sql
update orders
set pay_status = 1, status = 2
where number = ?
  and pay_status = 0
  and status = 1;
```

第一次影响 1 行，重复通知影响 0 行。真实支付还要核对签名、订单号、金额和第三方交易号。

## 5. Redis：缓存不是核心数据库

### 5.1 缓存未命中和连接失败

缓存未命中：

```text
Redis 连接正常，但 key 不存在
```

代码通常是：

```java
String value = redisTemplate.opsForValue().get(key);
// value == null
```

Redis 连接失败：

```text
Redis 没启动、地址错误、密码错误、网络异常或连接超时
```

通常会抛出连接异常。只有代码明确捕获异常并降级，才能继续查 MySQL。

### 5.2 缓存旁路模式

读取商品信息的典型流程：

```text
1. 查询 Redis
2. 命中，直接返回
3. 未命中，查询 MySQL
4. MySQL 查到后写入 Redis
5. 返回结果
```

Redis 连接失败时，只有在代码明确实现了异常降级时，才能执行：

```java
try {
    // 查询 Redis
} catch (Exception e) {
    // 查询 MySQL
}
```

Redis 不会自动帮你切换到 MySQL。

### 5.3 更新数据库和缓存

常见推荐顺序：

```text
先更新 MySQL
再删除 Redis 缓存
下次读取时从 MySQL 加载新数据
```

不建议先删除缓存再更新 MySQL，因为可能出现：

```text
A 删除缓存
B 读取 MySQL 旧数据
B 把旧数据写回 Redis
A 更新 MySQL
```

最后 Redis 仍然是旧数据。

通常选择“删除缓存”而不是“直接更新缓存”，因为：

- 一个业务数据可能有多个缓存 Key
- 组合查询缓存不容易全部更新
- 更新 Redis 失败会造成双写不一致
- 删除后可以由下一次查询重新构建

### 5.4 缓存三大问题

#### 缓存穿透

查询一个数据库中永远不存在的数据：

```text
Redis 没有
MySQL 也没有
每次请求都访问 MySQL
```

解决：

- 缓存短时间空值
- 校验 ID 格式和范围
- 布隆过滤器
- 限流

#### 缓存击穿

一个热门 Key 刚好过期，大量请求同时访问 MySQL。

解决：

- 互斥锁，只允许一个线程重建缓存
- 逻辑过期，后台刷新
- 热点数据预热
- 必要时让热点数据不过期

#### 缓存雪崩

大量 Key 同时过期，数据库压力突然升高。

解决：

- TTL 增加随机值
- 分批刷新
- 缓存预热
- 限流、熔断和降级
- Redis 高可用

记忆口诀：

```text
穿透：查不存在
击穿：一个热点失效
雪崩：一大片同时失效
```

### 5.5 哪些数据可以兜底

| 数据 | Redis 失败时能否直接查 MySQL |
|---|---|
| 商品缓存 | 通常可以，MySQL 保存核心数据 |
| 订单核心数据 | 应从 MySQL 查询 |
| 验证码 | 通常不能，可能只存在 Redis |
| 登录 Session | 通常不能，可能只存在 Redis |
| JWT | 取决于项目设计，JWT 本身可自验证 |
| 分布式锁 | 不能随便用 MySQL 查询替代 |

分布式锁不是普通数据。查 MySQL 不等于获得了锁，必须专门设计数据库锁或唯一约束方案。

### 5.6 RDB 和 AOF

- RDB：定期保存数据快照
- AOF：记录写命令，重启时重新执行

它们解决 Redis 重启后的数据恢复问题，不能解决当前应用连接不上 Redis 的问题。

## 6. WebSocket、定时任务和来单提醒

### 6.1 HTTP 与 WebSocket

HTTP 典型模式：

```text
客户端请求 -> 服务器响应
```

WebSocket：

```text
先通过 HTTP 握手升级
-> 返回 101 Switching Protocols
-> 建立长连接
-> 客户端和服务器都可以主动发送消息
```

来单提醒和催单适合 WebSocket，因为服务器可以主动推送，不需要前端不断询问。

### 6.2 只用 HTTP 怎么提醒

前端定时轮询：

```text
每隔几秒请求一次“是否有新订单”
```

缺点：

- 没有新订单时也产生请求
- 增加服务器和数据库压力
- 有延迟
- 需要处理重复提醒

### 6.3 `cron` 和 WebSocket 的关系

项目里的：

```java
@Scheduled(cron = "0/5 * * * * ?")
```

表示每 5 秒执行一次定时任务。它只负责“定时触发方法”，不是 WebSocket 能主动推送的根本原因。

真正让服务器推送的是已建立的 WebSocket `Session`：

```java
session.getBasicRemote().sendText(message);
```

可以这样区分：

```text
cron：什么时候执行
WebSocket Session：消息通过什么连接发送
```

### 6.4 WebSocket 建连排查

建议按顺序检查：

1. 后端是否启动并监听正确端口。
2. 前端拼出的完整地址是否正确，例如 `ws://127.0.0.1:8080/ws/客户端ID`。
3. 浏览器 Network 的 `WS` 页面中，握手是否返回 `101`。
4. `404` 通常检查路径，`401` 检查认证，`502` 检查代理和后端端口。
5. 后端是否打印连接建立日志。
6. 经过 Nginx 时，是否转发 `Upgrade` 和 `Connection` 请求头。
7. HTTPS 页面使用 `wss://`，避免混合内容被浏览器拦截。

## 7. Token、异常和 HTTP 状态码

### 7.1 Token 完整流程

```text
登录成功
-> 后端 JwtUtil 生成 JWT
-> 前端保存 Token
-> Axios 请求拦截器放入请求头
-> 后端 JWT 拦截器读取并解析
-> 取出 employeeId 或 userId
-> 放入 BaseContext
-> Controller 和 Service 使用当前登录身份
```

项目中商家端和用户端分别有 JWT 拦截器。无效 Token 通常响应：

```text
401 Unauthorized
```

### 7.2 全局异常处理器

全局异常处理器主要负责把异常统一转换为前端能识别的结果，不是负责自动定位某一行代码。

```text
Service 抛出业务异常
-> @RestControllerAdvice 捕获
-> @ExceptionHandler 处理
-> 记录日志
-> 返回 Result.error(msg)
```

例如：

```java
throw new OrderBusinessException("订单状态错误");
```

前端得到：

```json
{
  "code": 0,
  "msg": "订单状态错误"
}
```

异常堆栈用于开发者排错，不应该原样返回给用户。

### 7.3 常见 HTTP 状态码

```text
400：请求参数、格式或绑定不合法
401：没有登录或 Token 无效
403：已识别身份，但没有权限
404：路径或资源不存在
500：服务器内部未处理异常
```

400 不能直接等于 Token 错误。Token 问题通常先看 401。

## 8. Axios、请求参数和文件下载

### 8.1 `params` 与 `data`

GET 查询一般使用 `params`：

```typescript
request({
  url: '/report/top10',
  method: 'get',
  params: {
    begin: '2026-08-01',
    end: '2026-08-29'
  }
})
```

最终类似：

```text
/report/top10?begin=2026-08-01&end=2026-08-29
```

POST、PUT 提交或修改数据一般使用 `data`：

```typescript
request({
  url: '/admin/order',
  method: 'post',
  data: formData
})
```

不是简单根据数据量决定，而是根据 HTTP 请求语义决定：

```text
GET 查询条件 -> params
POST 新增数据 -> data
PUT 修改数据 -> data
```

### 8.2 `responseType: 'blob'`

Excel、PDF、ZIP、图片、音频等是二进制响应。Axios 下载 Excel 时：

```typescript
const { data } = await request({
  url: '/report/export',
  method: 'get',
  responseType: 'blob'
})
```

浏览器下载流程：

```text
后端输出二进制
-> Axios 按 Blob 接收
-> URL.createObjectURL 创建临时 URL
-> a 标签或其他下载方式触发保存
-> URL.revokeObjectURL 释放临时 URL
```

常见二进制类型：

```text
blob：交给浏览器下载、预览或播放
arraybuffer：JavaScript 需要读取和处理字节
json：普通接口数据
text：文本数据
```

除了 `a` 标签，还可以：

- `window.location.href` 直接打开带下载响应头的接口
- `window.open` 打开下载地址
- 使用 `FileSaver` 等库
- 使用 File System Access API 保存到用户选择的位置
- 使用表单提交让浏览器接管下载

`window.location.href` 更适合大文件，但不方便设置自定义 Token 请求头；Axios + Blob 更适合需要自定义请求头的接口。

### 8.3 页面一直 Loading 的排查

推荐写法：

```typescript
this.loading = true
try {
  const response = await request()
  // 处理成功响应
} catch (error) {
  // 显示错误
} finally {
  this.loading = false
}
```

排查顺序：

1. Network 中请求是否结束。
2. Promise 是否使用了 `await` 或正确 `return`。
3. 成功分支是否关闭 loading。
4. `catch` 分支是否关闭 loading。
5. 响应解析是否抛出异常。
6. Axios 拦截器是否正确返回 `response` 或 `Promise.reject(error)`。
7. 请求被取消、超时或重复请求后，是否仍执行 `finally`。

原则：无论成功、失败、超时，loading 都应该有明确的关闭路径。

## 9. Excel 类路径资源

报表模板位于：

```text
src/main/resources/template/运营数据报表模板.xlsx
```

使用：

```java
getClass().getClassLoader()
    .getResourceAsStream("template/运营数据报表模板.xlsx");
```

这是读取类路径资源。项目打成 JAR 后，模板可能位于 JAR 压缩包内部，不一定是普通磁盘文件，因此不能依赖本机绝对路径：

```text
D:/某台电脑/某个目录/模板.xlsx
```

报表下载还应该设置：

```http
Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
Content-Disposition: attachment;filename*=UTF-8''运营数据统计报表.xlsx
```

含义：

- `Content-Type`：告诉浏览器响应是什么类型
- `Content-Disposition`：告诉浏览器以附件方式下载，并提供文件名

如果 Excel 日期列出现 `BusinessDataVO(...)`，说明代码把整个对象调用了 `toString()`，应该取明确字段：

```java
row.getCell(1).setCellValue(data.getDateStr());
```

日期列表和营业额列表必须长度一致，并且相同下标表示同一天：

```text
dateList[0]    对应 turnoverList[0]
dateList[1]    对应 turnoverList[1]
```

## 10. 自增 ID、Git 和密钥

### 10.1 自增 ID 不连续

自增 ID 可能因为以下原因出现间隔：

- 插入后事务回滚
- 插入失败但 ID 已经申请
- 记录被删除
- 并发插入提前分配 ID
- 批量插入申请一段 ID

自增 ID 的主要职责是唯一标识，不是保证连续。订单展示编号、发票号等需要特殊规则时，应另外设计业务编号。

### 10.2 分支职责

```text
dev：日常开发和功能提交
master：稳定、可发布版本
```

正常流程：

```text
在 dev 开发
-> commit
-> push origin dev
-> 功能稳定后发起 Pull Request
-> 审核后合并 master
```

Pull Request 的价值是让代码在进入稳定分支前经过比较、讨论和检查。

### 10.3 分支不能解决密钥问题

即使是私有仓库，也不建议提交密码、Token、API Key 和私钥，因为：

- 提交历史可能永久保留
- 仓库权限可能扩大
- 日志、压缩包和镜像也可能带出密钥
- 密钥一旦泄露通常需要立即轮换

正确方式：

```text
本地：application-local.yml 或 .env
提交：application-local.yml.example
服务器：环境变量或配置中心
Git：.gitignore 忽略本地配置
```

如果密钥曾经提交过，仅删除当前文件还不够，还需要清理历史并轮换密钥。

## 11. 常见故障的系统排查模板

### 11.1 接口返回 400

```text
1. 浏览器 Network：URL、Method、Query、Payload、Headers、Response
2. 参数名称、类型、格式、必填字段
3. GET 是否使用 params，POST/PUT 是否使用 data
4. Token 是否存在，以及是否应该返回 401
5. 后端 Controller 是否成功绑定参数
6. Service 是否主动抛出业务异常
7. Mapper SQL 和数据库字段
8. DataGrip 查看实际数据和约束
```

### 11.2 WebSocket 连不上

```text
1. 后端是否启动
2. 端口是否正确
3. ws/wss 协议是否正确
4. /ws/{sid} 路径是否正确
5. 浏览器 WS 握手是否为 101
6. Nginx 是否支持 Upgrade
7. 后端是否出现 ServerContainer 或映射错误
```

### 11.3 统计图表不正确

```text
1. 日期范围是否正确
2. dateList 和数据列表长度是否一致
3. GROUP BY 是否丢失无数据日期
4. 缺失日期是否补 0
5. COUNT 的 0 和 SUM 的 NULL 是否处理
6. 订单状态是否只统计已完成订单
7. 前端 split(',') 后是否得到正确数组
```

### 11.4 Excel 导出失败

```text
1. 前端是否使用 responseType: blob
2. URL 是否为 /report/export
3. 后端模板是否位于 resources/template
4. getResourceAsStream 路径是否写成 template/xxx
5. inputStream 是否为空
6. Sheet、行、单元格是否存在
7. 日期是否取明确字段
8. Content-Type 和 Content-Disposition 是否正确
9. 数据库统计是否先正常返回
```

## 12. 最终记忆清单

```text
事务：保证一组数据库操作要么全成功，要么全失败。
catch：异常被吃掉，事务可能无法回滚。
@Param：给 MyBatis 参数建立 SQL 名称映射。
#{ }：预编译参数；${ }：文本替换，可能有注入风险。
COUNT 没数据是 0；SUM 没数据通常是 NULL。
GROUP BY 不会凭空生成没有记录的日期。
INNER JOIN 不保留匹配失败的左表记录。
状态流转必须由后端控制，不能相信前端 status。
幂等：重复请求不会重复产生业务结果。
缓存未命中和 Redis 连接失败不是一回事。
更新缓存：通常先更新 MySQL，再删除 Redis。
穿透查不存在，击穿一个热点，雪崩一大片。
cron 决定定时执行，WebSocket Session 负责长连接推送。
Token 错误通常是 401，不要把所有错误都判断成 400。
GET 用 params，POST/PUT 通常用 data。
文件响应使用 blob，JavaScript 要处理字节时可使用 arraybuffer。
类路径资源不能依赖本机绝对路径。
dev 开发，master 稳定；分支不能代替密钥管理。
```

## 13. 自测标准答案方向

以后遇到项目问题，回答不能只说“看日志”，应至少包含：

```text
现象 -> 请求证据 -> 后端日志 -> 代码层次 -> 数据库证据 -> 修复方案 -> 验证结果
```

例如“订单提交 400 且商家没有来单提醒”：

```text
先看前端请求是否真的发出
-> 看 URL、参数和 Token
-> 确认是否进入 Controller
-> 查看 Service 业务校验
-> 查看事务是否成功
-> 确认订单和订单明细是否写入 MySQL
-> 确认支付状态是否变更
-> 最后检查 WebSocket 是否有连接并成功推送
```

这就是从现象到证据的完整排查思路。
